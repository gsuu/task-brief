# task-brief 설계

- 작성일: 2026-11-27
- 상태: 설계 승인, 스펙 검토 대기
- 이름 `task-brief`는 임시 이름이다. 저장소와 주소가 정해지면 맞춰 바꾼다.

## 1. 목표

주니어 웹퍼블리셔가 프롬프트를 잘 쓰도록 생각을 넓혀준다. 프롬프트를 대신 만들어 주는 것이 목적이 아니라, 쓰는 과정에서 놓친 것을 알게 하는 것이 목적이다.

이 도구가 효과가 있는지는 **태스크별 Claude Code 작업 토큰**으로 잰다. 관리자가 사용량과 원인을 보고, 지시문을 고치고, 다시 재서 계속 줄여 간다.

### 결정 기준

설계와 구현에서 결정이 필요할 때 아래 순서로 확인한다.

1. 간편한가 (자주 쓰려면 간편해야 한다)
2. 목표에 맞는가
3. 토큰을 줄이는가

### 간편함 상한

| 항목 | 상한 |
| --- | --- |
| 처음 설치 | 명령 한 줄, 한 번 |
| 태스크마다 주니어가 하는 일 | 쓰기, 답하기, 붙여넣기 |
| 창 전환 | 1번 (사이트 → Claude Code) |
| 필수 입력 | 목표 한 칸 |
| 확인 질문 | 최대 3개 |
| 놓친 것 짚기 | 최대 3개 |

상한은 채워야 하는 수가 아니다. 문구 수정 같은 작은 태스크는 질문 없이 바로 프롬프트가 나온다.

## 2. 범위

### 만드는 것

| 부분 | 내용 |
| --- | --- |
| 사이트 | 회사 서버에 FTP로 올린다. 주니어 화면, 서버 스크립트(AI 호출), 태스크 기록, 관리자 화면 |
| Claude Code 연결 | 작업이 끝나면 토큰 사용량과 많이 쓴 이유를 사이트로 보낸다 |

### 만들지 않는 것 (이번 범위 밖)

- cttd-skills 정식 등록 (테스트 후 진행)
- 사이트에서 Claude Code 작업을 바로 실행하는 기능
- 사람별 구분과 로그인
- PSD 읽기 도구를 팀 표준으로 정하는 일
- 프로젝트 코드를 사이트가 직접 읽는 기능

## 3. 주니어 흐름

| 순서 | 어디서 | 하는 일 |
| --- | --- | --- |
| 1 | 사이트 | 입력 칸을 채운다 |
| 2 | 사이트 | 확인 질문과 놓친 것 짚기에 답한다 (없으면 건너뛴다) |
| 3 | 사이트 → Claude Code | 완성된 프롬프트를 복사해 붙여 넣는다 |

주니어는 일할 때마다 사이트에 온다. 프로젝트는 매번 다르다.

### 입력 칸

| 칸 | 필수 | 칸 아래 안내 |
| --- | --- | --- |
| 목표 | 필수 | 무엇을, 왜 만드나요? |
| 꼭 할 것 | 선택 | 프리셋을 체크로 정하고, 직접 입력도 받는다 |
| 하지 말 것 | 선택 | 프리셋을 체크로 정하고, 직접 입력도 받는다 |
| 자료 | 선택 | 피그마 주소, 이미지, PSD, 기획서 |

완료 기준은 주니어가 처음부터 쓰지 않는다. 도구가 목표를 읽고 먼저 제안하며, 주니어는 확인 단계에서 고치거나 그대로 둔다.

프리셋은 웹퍼블리싱에서 자주 나오는 항목을 고정 목록으로 두고 시작한다. 시니어가 검토해 고친다.

프로젝트에서 늘 지켜야 하는 것은 사이트에 쓰지 않는다. 프로젝트 규칙 문서에 두고 Claude Code가 매번 읽는다.

기본 규칙 두 개는 쓰기 화면에 읽기 전용 문구로 항상 보여 준다.

### 확인 질문

- 답에 따라 결과가 달라지는 것만 묻는다.
- 확인 단계의 첫 화면은 제안한 완료 기준이다. 주니어가 고치거나 그대로 두고 넘어간다. 이 화면은 질문 수 상한에 세지 않는다.
- 하나씩, 가능하면 보기를 주고 묻는다.

### 놓친 것 짚기

시니어가 "이것까지 생각해 봤나요?" 하고 묻는 단계다. 질문마다 **왜 묻는지 한 줄**을 붙인다. 주니어는 "해당 없음"으로 넘길 수 있다.

우선순위는 아래 순서다.

1. 일관성: 이미 있는 컴포넌트나 방식으로 되지 않는가
2. 과함: 이 화면에 그 스크립트나 구조가 필요한가
3. 상태와 예외: 내용이 없을 때, 글이 길 때, 불러오는 중, 오류
4. 반응형: 좁은 화면과 넓은 화면
5. 접근성: 키보드 조작, 대체 텍스트

사이트는 프로젝트 코드를 볼 수 없다. 그래서 1번과 2번은 "비슷한 기존 화면이 있나요?"처럼 주니어가 떠올리게 하는 질문으로 묻고, 실제 확인은 프롬프트의 지시로 Claude Code가 한다.

이 관점 목록은 저장소의 `senior-checks.md`에 두고 시니어가 PR로 늘려 간다.

### 화면 디자인

시안: https://claude.ai/artifact/XJeP2BjNV7t97zUbQE5cLA

한 번에 하나만 보여 준다. 쓰기, 확인, 프롬프트가 같은 페이지에서 차례로 바뀐다. 페이지를 이동하지 않는다.

| 화면 | 보이는 것 |
| --- | --- |
| 쓰기 | 목표 한 칸과 "다음" 버튼. 그 아래에 꼭 할 것, 하지 말 것(프리셋 체크와 직접 입력), 자료 칸을 처음부터 펼쳐 둔다. 눌러서 펼치는 버튼은 두지 않는다 |
| 확인 | 위에 목표를 회색으로 남긴다. 첫 화면은 제안한 완료 기준을 고치는 칸. 이어서 질문 하나, 이유 한 줄, 보기. "2 / 3"으로 진행을 표시한다. "이전"으로 돌아갈 수 있다 |
| 프롬프트 | 태스크 번호, 완성된 프롬프트, "복사" 버튼, "새 태스크". 프롬프트는 화면에서 바로 고칠 수 있고, 복사는 고친 내용을 가져간다 |

디자인 규칙은 아래와 같다. 장식 요소는 두지 않는다.

- 색은 흰색(#FFFFFF), 검정(#111111), 회색(#6B6B6B), 선(#E5E5E5)만 쓴다. 강조색은 없다.
- 글꼴은 고딕 한 가지(Noto Sans KR)를 쓰고, 프롬프트만 고정폭 글꼴을 쓴다.
- 글자 크기는 28, 16, 14 세 단계로 위계를 만든다.
- 입력 칸에 상자를 두지 않는다.
- 쓰기 화면의 구역(목표, 꼭 할 것, 하지 말 것, 자료)은 선 없이 넓은 여백으로 나누고, 구역 이름은 굵은 검정으로 쓴다. 가는 선은 확인 화면의 보기 목록과 프롬프트 칸에만 쓴다.
- 화면마다 검은 버튼은 하나다.
- 본문 폭은 최대 640px로 가운데에 둔다.
- 모든 화면 아래에 "© 2026 cttd.co.kr"을 회색 13px로 둔다.
- 기본 규칙 두 개는 쓰기 화면 아래에 회색 두 줄로 둔다.
- 화면 문구는 해요체로 쓰고, 단정하지 않는다("오해받을 수 있어요"). 프롬프트 본문은 평서체를 유지한다.

### 기본 규칙

| 규칙 | 지시 |
| --- | --- |
| 일관성 | 작업 전에 프로젝트 규칙 문서(CLAUDE.md, README, 린트·포매터 설정)와 비슷한 기존 화면·컴포넌트를 먼저 읽는다. 이름, 폴더 구조, 마크업과 CSS 작성 방식은 기존 것을 따른다. 이미 있는 컴포넌트는 새로 만들지 않는다. 다르게 해야 하면 이유를 말하고 먼저 묻는다 |
| 과하지 않게 | 요청한 것만 만든다. 요청하지 않은 기능, 옵션, 라이브러리를 넣지 않는다. HTML과 CSS로 되는 것에 스크립트를 쓰지 않는다 |

### cttd 스킬 매칭

| 작업 유형 | 스킬 |
| --- | --- |
| 화면이나 컴포넌트 구현 | `ui-component-builder` (피그마가 있으면 `design-to-code-analysis` 먼저) |
| 디자인과 맞는지 확인 | `visual-qa` |
| 브라우저, 모바일 확인 | `browser-testing` |
| 접근성 확인 | `a11y-specs` |
| 기존 사이트 파악 | `web-ui-analysis` |
| 해당 없음 | 스킬 없이 진행 |

스킬 목록(이름, 설명, 필요한 입력)은 cttd/skills의 `SKILL.md` frontmatter에서 스크립트로 뽑아 사이트 저장소에 JSON으로 둔다.

### 스킬 설치 지시

- 필요한 스킬이 없으면 그 스킬만 내려받은 뒤 진행한다.
- 프로젝트 폴더가 아니라 개인 영역에 설치한다. 프로젝트 저장소에 파일이 생기면 일관성 규칙에 어긋난다.
- 설치에 실패하면 이유를 알리고 스킬 없이 진행한다.

### 자료 지시

- PSD는 연결된 도구가 있으면 그것으로 읽고, 없으면 직접 읽어 보고, 안 되면 PNG로 내보내 달라고 요청한다.

### 마무리 점검 지시

작업이 끝나면 아래를 보고한다.

- 완료 기준별 충족 여부
- 기존 방식과 달라진 부분
- 요청 범위를 넘은 부분

## 5. 구성

### 사이트

| 단위 | 하는 일 | 의존하는 것 |
| --- | --- | --- |
| 주니어 화면 | 입력, 질문과 답, 프롬프트 표시와 복사 | 서버 스크립트 |
| 분석 함수 | 입력과 자료를 받아 작업 유형, 쓸 스킬, 확인 질문, 놓친 것을 돌려준다 | AI 호출, 스킬 목록, `senior-checks.md` |
| 프롬프트 함수 | 입력과 답을 받아 완성된 프롬프트를 만든다 | 지시문 틀 |
| 기록 저장 | 태스크와 사용량을 저장하고 조회한다 | 저장소 |
| 사용량 수신 함수 | Claude Code가 보낸 사용량을 태스크 번호에 붙여 저장한다 | 기록 저장 |
| 관리자 화면 | 기록을 표로 보여 준다 | 기록 저장 |

화면은 정적 페이지로, 서버 쪽은 회사 서버가 실행할 수 있는 언어의 스크립트로 만든다. FTP 호스팅에서 흔한 PHP를 기본으로 가정하고, 0단계에서 서버 환경을 확인한 뒤 확정한다. 프레임워크는 쓰지 않는다. 표의 "함수"는 이 서버 스크립트 하나하나를 가리킨다.

### 배포

- 저장소에 올리면 GitHub Actions가 FTP로 배포한다. cttd-skills의 `add-deploy-bot`이 만드는 방식을 그대로 쓴다.
- FTP 접속 정보는 저장소 시크릿에 둔다.

### 서버가 갖춰야 하는 것

AI를 부르고 기록을 남기려면 서버에서 프로그램이 돌아야 한다. 파일만 내려주는 서버로는 API 키를 숨길 수 없다.

| 조건 | 이유 |
| --- | --- |
| 서버 스크립트 실행 (PHP 등) | API 키를 브라우저에 내보내지 않고 AI를 부른다 |
| HTTPS | 암호와 올린 자료가 그대로 오가지 않게 한다 |
| 밖으로 나가는 HTTPS 호출 허용 | 서버가 Claude API를 부른다 |
| 웹에서 열리지 않는 경로나 접근 차단 설정 | API 키 파일과 기록 파일을 둔다 |
| 실행 시간 제한이 충분함 | AI 응답을 기다리는 동안 끊기지 않아야 한다 |
| 저장소 (DB 또는 파일) | 태스크와 사용량을 기록한다 |

조건이 맞지 않으면 화면은 FTP 서버에 두고 서버 스크립트만 다른 곳(예: Vercel)에 두는 방법으로 바꾼다. 이 판단은 0단계에서 한다.

지시문 틀(완성된 프롬프트의 고정 부분)은 화면 코드와 분리해 파일 하나로 둔다. 지시문을 고치는 일이 가장 잦기 때문이다. 틀에는 버전 번호를 두고 태스크마다 기록한다.

### AI 호출

- 서버 스크립트에서만 부른다. API 키는 서버의 설정 파일에 두고, 그 파일은 웹에서 열리지 않게 한다. 저장소에는 넣지 않고 배포 대상에서도 뺀다. 서버에 한 번 직접 올린다.
- 태스크당 호출은 분석 한 번이다. 분석은 완료 기준 제안, 쓸 스킬, 확인 질문, 놓친 것을 돌려주고, 보기마다 프롬프트의 어느 구역에 어떤 줄로 들어갈지를 함께 준다.
- 프롬프트는 AI가 쓰지 않는다. 입력, 답, 지시문 틀을 규칙대로 조립한다. 기본 규칙이 빠지거나 바뀌는 일을 막고 토큰을 줄이기 위해서다.

### 접근 제한

- 팀 공용 암호를 처음 한 번 입력한다. 브라우저가 기억한다.
- 관리자 화면은 주니어 화면에 링크를 두지 않는다. 관리자가 주소를 직접 열고 별도 암호를 입력한다.
- 사이트용 API 키는 새로 발급하고 월 사용 한도를 건다.

### 기록 구조

| 묶음 | 항목 |
| --- | --- |
| 태스크 | 번호, 만든 시각, 작업 유형, 입력 내용, 질문과 답, 완성된 프롬프트, 지시문 버전, 사이트에서 쓴 토큰 |
| 사용량 | 태스크 번호, 토큰 수(입력, 출력, 캐시), 원인 분류, 받은 시각 |

올린 자료 원본은 프롬프트가 완성되면 지운다. 기록에는 글만 남긴다.

### 원인 분류

| 분류 | 뜻 |
| --- | --- |
| 넓게 읽음 | 관련 없는 파일까지 많이 읽었다 |
| 수정 반복 | 같은 부분을 여러 번 고쳤다 |
| 확인 반복 | 스크린샷이나 브라우저 확인을 여러 번 했다 |
| 자료가 큼 | 디자인이나 기획서가 컸다 |
| 되물음 | 목표가 모호해 작업 중에 다시 물었다 |
| 스킬 설치 | 스킬을 내려받는 데 썼다 |
| 기타 | 위에 해당하지 않는다 |

### 관리자 화면

| 보는 것 | 용도 |
| --- | --- |
| 작업 유형별 평균과 추이 | 같은 유형끼리 비교해 줄었는지 본다 |
| 많이 쓴 태스크 순 목록 | 어디부터 볼지 정한다 |
| 원인 분류별 횟수 | 가장 잦은 원인을 찾는다 |
| 지시문 버전별 비교 | 지시문을 고친 효과를 확인한다 |

## 6. 오류 처리

| 상황 | 처리 |
| --- | --- |
| AI 호출 실패 | 질문 없이 입력 내용과 지시문 틀만으로 프롬프트를 만들어 준다. 실패했다는 안내를 한 줄 보여 준다 |
| 자료를 읽지 못함 | 그 자료는 경로나 주소로만 프롬프트에 넣고, Claude Code가 읽게 한다 |
| 사용량 전송 실패 | 작업을 막지 않는다. 그 태스크는 사용량 없음으로 남는다 |
| 태스크 번호 없이 온 사용량 | 버린다 |

## 7. 테스트

| 대상 | 방법 |
| --- | --- |
| 프롬프트 함수 | 단위 테스트. 고정 부분이 항상 들어가는지, 빈 칸이 줄로 남지 않는지 |
| 분석 함수 | 단위 테스트. 질문과 짚기가 각각 3개를 넘지 않는지, 응답 형식이 깨지면 질문 없이 진행하는지 |
| 사용량 수신 함수 | 단위 테스트. 번호가 맞는 태스크에만 붙는지 |
| 전체 흐름 | 대표 태스크 5개(큰 구현, 작은 수정, 디자인 확인, 접근성 확인, 자료 없는 태스크)로 직접 돌려 보는 점검표 |

테스트 기간에 볼 것은 아래 네 가지다.

- 확인 질문과 놓친 것 짚기가 쓸모 있었는가
- 주니어가 중간에 그만두지 않았는가
- 결과물이 기존 프로젝트 방식을 지켰고 과하지 않았는가
- 일주일 뒤에도 태스크마다 쓰고 있는가

## 8. 만드는 순서

단계마다 구현 계획을 따로 세운다.

| 단계 | 내용 | 끝났다고 보는 기준 |
| --- | --- | --- |
| 0 | 시험 두 가지: 회사 서버 환경 확인, Claude Code 작업 토큰을 태스크 번호와 묶어 자동으로 보낼 수 있는지 확인 | 서버 조건 표를 모두 확인했다. 실제 Claude Code에서 태스크 하나를 돌렸을 때 정확한 토큰 수가 태스크 번호와 함께 도착한다 |
| 1 | 주니어 화면, 분석 함수, 프롬프트 함수 | 대표 태스크 5개가 점검표를 통과한다 |
| 2 | 기록 저장, 사용량 수신, 관리자 화면, Claude Code 연결 설치 | 태스크를 돌리면 관리자 화면에 사용량과 원인이 보인다 |

### 0단계에서 시험할 방법

서버 환경은 작은 시험 스크립트 하나를 올려 확인한다. 스크립트 실행 여부와 버전, 밖으로 나가는 호출, 실행 시간 제한, 쓸 수 있는 저장소를 본다.

토큰 수집은 아래 순서로 시험하고, 먼저 되는 것을 쓴다.

1. 작업이 끝날 때 실행되는 훅이 대화 기록의 사용량을 합산해 사이트로 보낸다.
2. Claude Code의 사용량 내보내기 기능(OpenTelemetry)을 사이트로 향하게 설정한다.
3. 둘 다 안 되면 사용량은 Console의 키별 수치로만 보고, 태스크별 기록은 원인 보고만 받는다.

한 대화에서 태스크 여러 개를 이어서 하면 사용량이 섞인다. 시험에서 태스크 번호가 나온 시점으로 나눌 수 있는지 확인하고, 안 되면 "태스크마다 새 대화"를 안내한다.

원인 분류는 Claude Code가 마무리 점검 때 스스로 정해 보내는 방식으로 시작한다.
